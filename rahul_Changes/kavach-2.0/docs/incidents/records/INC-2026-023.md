## Symptoms

NIFTY feed task exited repeatedly with [WinError 5] Access is denied replacing data/nifty_ltp_cache.json, followed by watchdog restarts and KAVACH stale-cache pauses

## Business impact

Operator saw repeated reconnect-style feed churn while the upstream WebSocket could still connect successfully.

## Technical impact

Local cache persistence failure was misclassified as feed-task death, which triggered watchdog restarts and downstream stale-cache cascades.

## Trading impact

KAVACH/ATO lost fresh cache visibility and paused on stale reads even though the transport itself was not consistently failing.

## Root cause

write_nifty_ltp_cache() raised after a short Windows os.replace retry window. Transient file-lock races on nifty_ltp_cache.json therefore tore down the live feed task.

## Contributing factors

- Shared cache file is replaced frequently during market updates
- Windows file-lock races can block rename/replace longer than the prior retry window
- Feed watchdog treated any cache-write exception as a dead feed task

## Investigation

logs_uat/runtime/2026-06/2026-06-25/drishti/logs/all.log shows repeated WinError 5 cache-replace failures at 13:34, 13:35, and 13:39 IST with watchdog restarts after each exit.

## Fix implemented

Extended Windows-safe replace retries and changed NIFTY cache writes to log-and-return on persistent replace-lock races instead of raising and killing the feed task.

## Why this fix works

A transient local file lock should not be interpreted as a transport disconnect. The feed task now survives short-lived cache persistence races, reducing false restart and stale-cache cascades.

## Regression risk

If another process holds the cache file lock for several seconds, cache freshness can still degrade and KAVACH may still pause; however DRISHTI no longer enters a restart storm for the same local file issue.

## Preventive measures

- Keep Windows file-replace retries tuned for high-frequency cache writers
- Do not let local cache persistence failures tear down the transport task

## Lessons learned

- Not every feed-task exception is a network problem; local filesystem races can create transport-like symptoms
- Shared disk cache layers need their own resilience budget separate from WebSocket retry logic

## Future recommendations

- Add explicit telemetry for cache-write failure counts in DRISHTI health/status
- Consider harmonizing other high-frequency JSON writers with the same Windows retry policy
