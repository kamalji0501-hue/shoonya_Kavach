# Batman v3 - Implementation Tracker

Last updated: 2026-06-12
Purpose: Single operational tracker for what is coded, what is design-locked, and what is still pending.

## Conversation Capture Contract (Locked Process)

This tracker is now a mandatory update target for every meaningful conversation.

For each session where we discuss design, implementation, bugs, risks, or priorities:
1. Update the relevant row in the Master Feature Matrix (status/evidence/next action).
2. Add a timestamped entry in SESSION_CAPTURE_LOG.md.
3. If a new idea is approved but not coded, mark DESIGN_LOCKED_NOT_CODED.
4. If code is shipped but not wired in runtime, mark CODED_NOT_INTEGRATED.
5. If testing/production checks are still pending, keep OPS_VALIDATION_PENDING.

If no tracker update is needed in a session, we must add a log entry saying "No tracker delta" to keep audit continuity.

Primary log file: SESSION_CAPTURE_LOG.md

## Status Legend

- CODED: Implemented in code and available now.
- CODED_NOT_INTEGRATED: Implemented but not wired in the active runtime path.
- DESIGN_LOCKED_NOT_CODED: Requirements finalized in design docs, coding not started.
- PENDING_DESIGN: Still in idea or partial design stage.
- OPS_VALIDATION_PENDING: Code exists, but live/simulator/VPS validation is still pending.

## Session Update Protocol

When a design decision is locked:
1. Add or update a row in the Master Feature Matrix.
2. Set status to DESIGN_LOCKED_NOT_CODED unless already implemented.
3. Add concrete next action in one sentence.

When coding is completed:
1. Change status to CODED or CODED_NOT_INTEGRATED.
2. Update Evidence with actual file paths.
3. If runtime wiring still pending, keep CODED_NOT_INTEGRATED.

When validation is completed:
1. Move OPS_VALIDATION_PENDING items to CODED.
2. Add brief note in commit or session summary.

## Drift And Escalation Rules

These are "things going bad" early-warning rules.

1. If design says CODED but runtime is not wired, immediately downgrade to CODED_NOT_INTEGRATED.
2. If design and code disagree on behavior, mark affected feature row as at-risk and add a blocking next action.
3. If a blocker remains unresolved for 3 sessions, increase priority one level (Medium to High).
4. If production-risk feature has no validation evidence, keep OPS_VALIDATION_PENDING even if code exists.
